StructFlow · Product design case study · 2026

Know which projects make money, who delivered, and what is about to slip.

A structural design firm had three questions it could not answer quickly: project margin, each engineer's contribution, and delivery schedules. StructFlow puts projects, jobs, hours and payments in one workspace, and keeps the data fresh by making a job one typed line instead of an 11-field form.

  • MarginRevenue, staff cost and profit per project
  • ContributionLogged hours and on-time rate behind every bonus
  • ScheduleOverdue and due-soon work surfaced first

    Brief and research artifacts

    The inputs I was given, and what each one changed in the product.

    The firm wanted a single portal for staff, projects, jobs, files, milestones and payments, used internally and later by clients. Their questionnaire named three problems. I used them as the acceptance test for every screen.

      Research saidI designed

      04

      User flows

      Three of the fourteen I mapped: the ones that carry the business value, the AI design and the everyday experience.

      Swipe the chart sideways to follow the branches.

      Start User step Decision System does it Error Outcome

      Money follows the work

      • Milestones own the moneyThe brief ties payment to milestones, never to jobs. Jobs only say which milestone they count toward.
      • Two trigger modesThe payment request goes out automatically, or waits as Ready to invoice for the admin to approve.
      • Roles stay cleanThe team member never sees an amount. They finish work and the admin handles money.

      One line, with checks where it can be wrong

      • Type it, don't fill itOne sentence fills project, person, priority, date, estimate and type.
      • Doubt is a visible branchAn unclear project is flagged Needs review instead of guessed.
      • A way backEvery create ends with Undo, and Create another keeps the project for the next job.

      The shortest path to Done

      • Next thing firstMy Work orders jobs by due date, with Start and Done on the row.
      • Review is optionalIt is a status, not an approval gate, so small jobs are not held up.
      • Feedback closes the loopFinishing a milestone's last job tells the member the admin has been told.

      05

      Design decisions

      Nine calls that shaped how it looks and behaves, the last four from the feedback round. Every screenshot is live: click the pins.

      01 / CALM FIRST SCREEN

      Four numbers, two charts, one list

      The admin dashboard was overwhelming in the first pass. I cut it to what a principal checks each morning and let charts animate in so the eye has an order.

        Click a pin or a point on the screenshot

        02 / ROLES

        The role decides the product

        Admins get a business dashboard. Team members get My Work: their jobs, their hours and only the projects they were added to. No money anywhere.

          03 / DENSITY

          Calm tables you can scan

          Header band, softly striped rows, a tint on hover. Status is a pill with a dot and a word, never color alone.

            04 / SAFETY

            Fast to find, safe to change

            ⌘K finds anything, scoped by role. Critical actions name the consequence before they run, and every change ends in a toast with Undo.

              05 / ERRORS

              Design the failure, not just the happy path

              Sign-in covers empty fields, a bad email, a wrong password with the tries left, deactivated accounts, a 30-second lockout after five tries, Caps Lock and offline. There is no role picker: the account decides.

                06 / STRUCTURE

                Project, then milestones, then jobs

                The first version kept jobs in a flat list with stages beside them. The feedback made the order explicit, so a project now opens as one column per milestone with its jobs underneath. The six delivery stages became the starting milestones, and the progress bar is drawn from them.

                  07 / FOCUS FOR STAFF

                  The whole project in view, one milestone in focus

                  A team member needs the shape of the project without reading every job. Every milestone stays on screen: the active one in full, the rest as quiet outlines that open when selected.

                    08 / ACCESS

                    Access is given per project

                    Staff see only the projects they were added to. For each one the admin chooses whether they can add jobs or only view.

                      09 / TIME

                      A day, across every project

                      Hours are logged from the job where the work happened, or from this page. The page answers a different question: what did each day add up to, and on which projects?

                          PROJECT

                          Risk decides the friction

                          A misread ₹2.5Cr would create a ₹2.5Cr project. The value is spelled out and confirmed before anything is created. Jobs get no gate.

                            What I audited against, and what changed

                            I ran the forms through an AI-experience-design skill and treated each gap as a bug.

                            GapFix
                            Fills were invisibleAuto tags, plus "Why these?" that lists each assumption with its reason and an Undo.
                            Silent when unsureAn amber needs-review note and tag when the project or client can't be told.
                            A misread ₹2.5Cr would create a ₹2.5Cr projectFriction scales with risk: the value is spelled out and confirmed. Jobs get no gate.
                            The modal just closedAn outcome toast with Undo, and a Create another path.
                            A blank formStarter lines built from the firm's real clients, projects and people.
                            Assignee was a guessRanked by skill match, project membership and open workload, with Assign to me.
                            UNSURE

                            When it can't tell, it says so

                            Type a job with no project and the form does not guess. It flags the field and explains.

                                Honest note. The parser is deterministic today: rules and heuristics, no model call. Every fill carries a reason, so an LLM can replace parseTaskText later without changing the interface: detected, assumed, needs review.

                                Outcome and next

                                What shipped, and what I would not claim yet.

                                Delivered

                                • A working prototype: 12 screens, 2 roles, full create / edit / delete
                                • Smart-fill job and project creation with provenance and Undo
                                • ⌘K search, comments with history, attachments, confirmations
                                • A standalone design-system page with live components
                                • Backend handoff generated from one spec: OpenAPI, SQL and a written guide

                                Not yet

                                • No usability test yet. I have not measured time-to-create against the 11-field form.
                                • Data lives in the browser. The API layer is ready but not connected.
                                • The parser is rule-based. Next: an LLM behind the same interface.
